# Internationalization and encoding contract

The portfolio is bilingual (English + Spanish). Every text file in the
repository must be **UTF-8 without a BOM** so that builds, snapshots, and
generated PDFs render correctly on every platform.

## The contract

- **Encoding:** UTF-8.
- **BOM:** not allowed. A leading `U+FEFF` breaks some static-site tooling and
  must never be present.
- **Replacement characters:** `U+FFFD` must never appear. It is a symptom of
  invalid bytes or double-encoded text.
- **Double-encoded UTF-8:** sequences such as `Ã` or `Â` followed by a
  continuation byte (`0x80-0xBF`) must never appear. They are the tell-tale
  footprint of UTF-8 that was read as Latin-1 and then re-encoded.

Files that are covered:

- `web/src/**`, `web/tests/**`
- `data/**`, `github-activity/**`, `scripts/**`
- `worker/src/**`
- `docs/**`, `en/**`, `es/**`, `site/**`
- Root-level `*.json`, `*.yml`, `*.md`, `*.mjs`

Binary assets (images, fonts, PDFs) are skipped automatically.

## How to detect mojibake

### Local encoding test

```powershell
node --test web/tests/encoding.test.mjs
```

The test scans the repo for:

1. `U+FFFD` and common double-encoded sequences.
2. Invalid UTF-8 bytes (via round-trip decode).
3. A leading UTF-8 BOM.
4. A stray `}` rendered after `</head>` in `web/dist/`.
5. A source-level stray `}` at template top level in `.astro` files.

### Build-time dist check

```powershell
npm --prefix web run build
```

The `postbuild` script runs `scripts/check-dist-encoding.mjs`, which scans every
`web/dist/**/*.html` file for `U+FFFD`, BOM, and a stray `}` after `</head>`.
The build fails loudly if any are found.

### Quick manual check

```powershell
# Look for replacement characters in a specific file.
node -e "const t=require('fs').readFileSync('web/src/i18n/copy.ts','utf8'); console.log(t.includes('\uFFFD'));"

# Look for a BOM in any scanned file.
node -e "
const {readFileSync,readdirSync}=require('fs');
const {join}=require('path');
function walk(d){const out=[];for(const e of readdirSync(d,{withFileTypes:true})){const p=join(d,e.name);if(e.isDirectory())out.push(...walk(p));else out.push(p);}return out;}
for(const f of walk('web/src')){const b=readFileSync(f);if(b.length>=3&&b[0]===0xEF&&b[1]===0xBB&&b[2]===0xBF)console.log('BOM:',f);}
"
```

## How to fix it

### If the intended character is obvious

Open the file in an editor that explicitly saves as UTF-8 without BOM (VS Code,
Neovim, Notepad++). Replace the garbled sequence with the correct character and
save.

Common examples:

| Mojibake bytes | Correct character | Original intent |
|---|---|---|
| `C3 83 C2 A1` (`U+00C3 U+00A1`) | `á` | UTF-8 `C3 A1` read as Latin-1 and re-encoded |
| `C3 83 C2 B1` (`U+00C3 U+00B1`) | `ñ` | UTF-8 `C3 B1` read as Latin-1 and re-encoded |
| `C3 82 C2 BF` (`U+00C2 U+00BF`) | `¿` | UTF-8 `C2 BF` read as Latin-1 and re-encoded |
| `EF BF BD` (`U+FFFD`) | varies | Replacement character produced by invalid UTF-8 |

### If the correct text is ambiguous

Do not guess. Report the file and the surrounding context in the PR so a human
can confirm the intended text. Weakening the assertion is never the right fix.

## CI gate

The **Quality pipeline** (`.github/workflows/quality.yml`) enforces this
contract on every pull request and push to `main`:

- `Build web` runs `npm --prefix web run build`, which executes the
  `postbuild` gate (`scripts/check-dist-encoding.mjs`).
- `Encoding & stray-character regression` runs
  `node --test web/tests/encoding.test.mjs` against the freshly built output.

A commit that introduces mojibake, a BOM, or a stray brace fails the pipeline
before it can reach `main`.
